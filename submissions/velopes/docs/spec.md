# ВелоПес — специфікація (v1)

> Написано **до коду** (SDD). Зміни після зіткнення з реальністю — у розділі «Журнал змін» внизу,
> а не тихим переписуванням.

## Навіщо

Невеликий вебзастосунок для двох речей:

1. знайти **б/у велосипед або запчастину** серед оголошень;
2. **орендувати велосипед разом з екіпіруванням для собаки** (причіп, кошик, кріплення для повідця) на конкретні дати.

## Рішення щодо масштабу

| Рішення | Хто вирішив |
|---|---|
| Ідея: пошук б/у велосипедів і запчастин + оренда з екіпіруванням для собак | людина |
| Обрізати до MVP: без реєстрації, оплати, завантаження фото, реальної БД | агент запропонував, людина погодила |
| Стек Next.js + TypeScript + Vitest (той самий, що в демо курсу) | агент (людина віддала вибір) |
| Валюта €, знижка за довгу оренду, правило про фаркоп | агент — **відкрите питання до людини** |

## Поза межами v1

Акаунти, оплата, повідомлення між продавцем і покупцем, додавання оголошень через UI, фото,
деплой із постійним сховищем.

## Дані

- `data/listings.json` — оголошення продажу: `id, kind ("bike" | "part"), title, description,
  priceEur, city, condition ("як новий" | "добрий" | "задовільний"), frameSize? ("S"|"M"|"L"|"XL"), postedAt (ISO date)`.
- `data/rentals.json` — прокат:
  - `bikes`: `id, title, city, pricePerDayEur, trailerHitch (bool)`;
  - `equipment`: `id, title, pricePerDayEur, quantity, requiresHitch (bool)`.
- Бронювання — `.data/bookings.json` (не в git): `id, bikeId, equipmentIds[], from, to, createdAt`.

## Функціональні вимоги

### F1. Пошук оголошень (`lib/search.ts`, чиста функція)

- текстовий запит — без урахування регістру, по `title` і `description`; кілька слів = усі мають бути;
- фільтри: `kind`, `city`, `frameSize`, `minPrice`, `maxPrice` (межі включно);
- порожній фільтр = не фільтрує;
- сортування: `newest` (за `postedAt`, за замовчуванням), `price-asc`, `price-desc`;
- `minPrice > maxPrice` → помилка валідації, а не порожній результат.

### F2. Ціна оренди (`lib/rental.ts`)

- дати `from`/`to` — календарні дні, **обидва включно** (з 1 по 3 = 3 дні);
- ціна = (ціна велосипеда за день + сума цін екіпірування за день) × днів;
- **7 днів і більше → знижка 10 %** на весь підсумок;
- результат округлюється до цілих центів; рахуємо в центах, щоб не ловити похибки float.

### F3. Валідація бронювання

- `to >= from`; `from` не раніше «сьогодні» (сьогодні передається параметром — для тестів);
- максимум 30 днів;
- екіпірування з `requiresHitch: true` (причіп) — лише до велосипеда з `trailerHitch: true`;
- одне й те саме екіпірування двічі в одному бронюванні — помилка.

### F4. Доступність

- два інтервали перетинаються, якщо мають хоч один спільний день (включно);
- велосипед вільний, якщо немає жодного бронювання цього велосипеда, що перетинається;
- екіпірування вільне, якщо кількість бронювань, що перетинаються і містять його, `< quantity`.

### F5. UI

- `/` — пошук і фільтри по оголошеннях, результати карткам;
- `/rent` — список велосипедів для прокату; форма: дати + чекбокси екіпірування → показує ціну
  і помилки валідації/доступності, кнопка «Забронювати»;
- `POST /api/bookings` — валідує (F3 + F4) і зберігає; повертає `201` з бронюванням або `400`/`409` з повідомленням українською.

## Критерій готовності

`pnpm check` (typecheck + lint + tests) зелений; кожна вимога F1–F4 має тест; F5 — тест маршруту API.
